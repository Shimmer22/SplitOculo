# SplitOculo 渐进式实验主文档
**文档目的**：作为后续所有实验 agent 的统一入口，约束实验行为、记录规范、验收流程和渐进式研究路径。  
**适用范围**：所有在 `SplitOculo` 工程内进行可行性验证、方法实现、实验记录、结果验收的 agent。  
**优先级**：高于临时口头指令；若与具体实验文档冲突，以“主文档 + 对应实验文档”的组合为准。

---

# 1. 项目当前研究目标

本项目当前聚焦的论文方向不是一般性的动态压缩或工程优化，而是：

> 在带宽受限的端云协同 VLM 中，学习或构造“对最终答案保持仍然充分、且尽量必要”的视觉证据传输机制。

这意味着后续实验不能只围绕“更快”“更少 token”“更低 latency”展开，而必须优先回答以下问题：

1. 在更少通信预算下，最终答案是否仍能保持？
2. 选出的证据是否比 attention-aware / prompt-aware / fixed-budget 更“必要”？
3. 这套方法是否在 OCR、数字、细粒度辨别、图表等高证据敏感任务上更稳？
4. 是否存在一个可行的最小实现路径，能够证明该论文方向值得继续投入？

本主文档的实验规划，全部围绕上述四个问题服务。

# 2. 所有 agent 的统一行为约束

## 2.1 阅读约束
除第一个 agent 外，后续 agent **不得默认全量阅读整个工程仓库**。  
后续 agent 的默认阅读顺序必须是：

1. `docs/MASTER_EXPERIMENT_PLAN.md`
2. `docs/PROJECT_FRAMEWORK.md`
3. 自己对应的实验文档
4. 实验文档中明确列出的必要代码/脚本/模块

只有在实验文档明确不足以完成任务时，agent 才可继续局部阅读工程，并且必须在实验记录中说明：

- 为什么现有文档不足
- 新阅读了哪些文件
- 这些文件如何影响实验判断

## 2.2 修改约束
agent 不得在未完成小规模验证前进行大规模重构。  
默认允许的修改类型：

- 新增实验脚本
- 新增日志/指标统计
- 新增轻量 selector / baseline 实现
- 新增实验文档、验收单、结果汇总
- 对已有代码做最小侵入式接口适配

默认不允许的修改类型：

- 大规模目录重组
- 无实验依据的核心流程重写
- 将实验性代码直接覆盖主干稳定路径
- 在未形成小规模证据前启动大训练或大搜索

## 2.3 实验优先级约束
所有实验必须遵循：

> 先验证可跑通，再验证有效，再验证必要性，再扩大规模。

严禁一开始就做：

- 大规模训练
- 海量数据跑表
- 大范围超参搜索
- 多变量同时改动

## 2.4 记录约束
任何 agent 完成实验后，必须同步更新以下三类记录：

1. 对应实验文档
2. 对应实验结果文档
3. 对应验收单

若未更新记录，则视为实验未完成。

## 2.5 结果约束
agent 不得只报告“跑了”，必须明确写出：

- 实验目标
- 配置
- 数据/任务
- 指标
- 结果
- 失败点
- 对论文方向的判断
- 下一步建议

## 2.6 分支/工作区约束
默认在当前工作分支内操作，不自行创建复杂分支流程。  
若必须新建分支，需在实验文档中注明原因和分支名。

# 3. 文档体系与目录规范

本项目后续必须形成以下文档体系。

## 3.1 核心文档
- `docs/MASTER_EXPERIMENT_PLAN.md`
  - 本文档，定义整体实验路线、约束、阶段目标、验收规范

- `docs/PROJECT_FRAMEWORK.md`
  - 由第一个 agent 生成

  - 实验总索引
  - 记录所有实验编号、状态、负责人、起止时间、结论摘要

## 3.2 实验目录
统一建立：

- `docs/experiments/`

在其下按实验编号建立子目录：

- `docs/experiments/EXP-001-bootstrap-baseline/`

- `docs/experiments/EXP-002R-reference-protocol/`
- `docs/experiments/EXP-003-selector-mvp/`
- `docs/experiments/EXP-004-necessity-check/`
- `docs/experiments/EXP-005-discriminative-check/`
- ...

每个实验目录内至少包含：

- `README.md`
  - 实验目标、假设、涉及模块、运行方式、结果摘要

- `RESULTS.md`
  - 详细结果、表格、失败案例、观察、结论

- `ACCEPTANCE.md`
  - 验收单，必须按模板逐项填写

必要时可加：

- `NOTES.md`
- `TODO.md`
- `artifacts/`
- `figures/`

# 4. 整体框架文档的职责与规范

`docs/PROJECT_FRAMEWORK.md` 的目的是让后续 agent **尽量不需要全量读仓库**。

## 4.1 它必须包含的内容
1. 工程目标与当前研究定位
2. 目录结构总览
3. 关键模块说明
4. 边端—云端主流程说明
5. 当前已有实验能力
6. 如何运行最小闭环
7. 数据与模型依赖说明
8. 哪些模块相对稳定、哪些模块适合实验改动
9. 当前已知问题、坑点、注意事项
10. 建议后续 agent 阅读路径

## 4.2 它不能做的事
1. 不能把仓库内容简单复制一遍
2. 不能只列目录，不解释模块关系
3. 不能省略运行方式与坑点
4. 不能写成泛泛 README
5. 不能脱离当前研究方向

## 4.3 对后续 agent 的作用
后续 agent 默认只允许基于：

- 主文档
- 整体框架文档
- 自己的实验文档

来理解项目和推进实验。

# 5. 渐进式实验路线总览

本项目后续实验必须按阶段推进。

---

## 阶段 A：工程理解与最小基线复核
### 目标
确认当前 SplitOculo 主干路径、运行方式、已有指标、已有瓶颈是否被正确理解，并形成后续实验的统一认知基础。

### 产物
- `docs/PROJECT_FRAMEWORK.md`
- `docs/EXPERIMENT_INDEX.md`
- `EXP-001` 实验目录
- 最小可运行基线结论

### 阶段完成标准
- 后续 agent 不必全量阅读仓库即可上手
- 已明确当前可跑通路径、关键脚本、指标和限制
- 已明确后续实验应该优先插入的模块位置

---

## 阶段 B：答案保持型评测基线建立
### 目标
在不引入新方法前，先建立论文真正需要的基础指标，不再只看 accuracy / latency，而要加入：

- answer agreement under budget
- token/bit budget
- OCR/细粒度子集表现
- 基础 attention-aware / prompt-aware 对照

### 产物
- `EXP-002`
- 基线评测脚本
- 基线结果表
- 至少一种 answer agreement 统计方法

### 阶段完成标准
- 能稳定比较不同传输预算下的答案保持能力
- 能生成后续 selector 方法复用的统一评测入口

---

## 阶段 B+：参考口径固化（Reference Protocol）
### 目标
把“后续实验到底以什么作为参考答案/参考分布”这个问题单独固化为可复用协议，避免各实验各自定义口径导致不可比。

### 产物
- `EXP-002R`
- 参考口径文档（teacher answer / teacher logits / 后处理规则）
- 评测集字段规范（prompt/reference/subset）
- 口径版本记录与变更说明

### 阶段完成标准
- 后续实验使用同一套参考口径即可直接比较
- 明确哪些指标用于快速筛选，哪些指标用于论文主结论

---

## 阶段 C：最小可行方法验证（MVP）
### 目标
实现最小可行的 answer-preserving selector，不追求最优，只追求验证“这个方向能否比固定预算/attention-aware 更像正确方向”。

### 推荐最小形式
- 冻结主干
- 新增轻量 selector
- 先做 top-k 选择
- 先只优化或模拟：
  - sufficiency
  - budget

### 产物
- `EXP-003`
- selector MVP
- 小规模实验结果
- 是否值得继续的判断

### 阶段完成标准
- 至少在一个小规模数据切片上看到正向信号
- 若无正向信号，明确失败原因和替代路径

---

## 阶段 D：必要性验证
### 目标
验证该方法不是简单 relevance-aware，而是真的更接近 necessity-aware。

### 推荐实验
- complement degradation
- selected-set deletion
- failure case 对照
- 与 attention-aware / prompt-aware 的局部案例比较

### 产物
- `EXP-004`
- necessity 相关图表和案例分析

### 阶段完成标准
- 至少一项实验证明：本方法选出的证据更“不可替代”

---

## 阶段 E：区分性与决策边界验证
### 目标
验证方法不只是支持正确答案，还更能区分竞争答案，尤其在数字、颜色、方向、OCR、图表上。

### 推荐实验
- competing-answer margin
- 易混淆样本集
- counterfactual-style perturbation analysis

### 产物
- `EXP-005`
- discriminative 分析文档

### 阶段完成标准
- 证明本方法不只是“相关”，还更接近“决策边界证据”

---

## 阶段 F：扩大规模实验
### 前提
只有当前面阶段已经证明可行，才允许进入大规模实验。

### 目标
- 更全面数据
- 更稳定统计
- 更完整表格
- 消融实验
- 大规模训练或系统优化

### 禁止事项
在阶段 C/D/E 尚未形成明确可行性证据前，不得直接进入本阶段。

# 11. 当前推荐的首批实验规划

## EXP-001：Bootstrap & Baseline Recovery
目的：
- 建立整体框架文档
- 确认工程可运行路径
- 确认已有指标与当前论文方向之间的差距

## EXP-002：Answer Agreement Baseline
目的：
- 建立答案保持型评测基线
- 引入通信预算和答案一致率指标
- 为后续方法比较准备统一评测口径

## EXP-002R：Reference Protocol
目的：
- 将“参考答案/参考分布”的确定过程独立成实验
- 固化 teacher reference（answer/logits）与后处理规则
- 作为 EXP-003 及之后实验的统一比较基础

## EXP-003：Selector MVP
目的：
- 用最小可行 selector 验证该方向是否有信号
- 只追求小规模验证，不追求最终最优

## EXP-004：Necessity Check
目的：
- 证明方法不是单纯 relevance-aware
- 检查补集退化和局部删除退化

## EXP-005：Discriminative Check
目的：
- 证明方法在竞争答案边界上更有优势
- 优先看 OCR、数字、颜色、方位、细粒度样本

# 12. 对后续 agent 的执行原则

后续 agent 必须遵守：

1. 不要越阶段推进
2. 不要省略记录
3. 不要在没有小样本证据时做大实验
4. 不要把工程整理工作当成研究结论
5. 不要把 relevance-aware 误写成 necessity-aware
6. 不要只汇报“效果变好了”，必须说明：
   - 对答案保持是否更好
   - 对必要性是否更强
   - 对论文主张是否构成支持

---

# 13. 当前项目的核心判断标准

后续所有实验，都应围绕以下三个判断标准：

## 标准 1：是否更保答案
同样预算下，是否更能保持 full-model 或 full-feature 的答案。

## 标准 2：是否更少冗余
选中的证据是否更接近“缺了会伤答案”的必要证据，而非宽泛相关内容。

## 标准 3：是否值得扩大规模
当前结果是否足以支持更重训练、更大数据、更复杂实现。

若三条都不能回答清楚，则不得进入大规模阶段。

# 14. 主文档维护规则

本主文档不是静态文件。  
但任何 agent 修改它时，必须满足：

1. 只能修改与实验路线、阶段划分、统一规范有关的内容
2. 不得将局部实验细节直接写进主文档
3. 重大修改必须在对应实验结果文档中说明理由

# 15. 最终执行口令约定

未来对 agent 的驱动口令约定如下：

- 对第一个 agent：
  - “阅读第一个 agent 文档，完成其中要求”

- 对后续 agent：
  - “阅读主文档以及整体框架文档，接着完成实验 EXP-xxx”

因此，所有 agent 必须确保：
- 主文档可单独约束行为
- 整体框架文档可单独帮助理解工程
- 实验文档可单独指导该实验执行

---

# 16. 最终目标

本主文档服务的最终目标不是完成若干零散实验，而是形成一条清晰、可复现、可扩展的论文验证路径：

> 从工程可运行，到答案保持型指标建立，到最小可行方法验证，到必要性与区分性证明，再到大规模实验。

所有 agent 的工作，都必须服务于这条主线。
